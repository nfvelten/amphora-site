<En>
Model Context Protocol (MCP) has become the default way to connect AI agents — Cursor, Claude Code, and others — to external tools: filesystems, databases, APIs. The protocol is well-designed. One thing it deliberately leaves out is authentication and authorization.

That's a reasonable choice for a protocol spec. It's a problem in practice.

---

## The gap

An MCP server exposes tools. Any client that can reach the server can call any tool. There's no concept of per-client permissions, no rate limiting, no audit trail. If you run a filesystem server that can write files and two agents connect — one trusted, one not — they both get the same access.

The standard answer is "put it behind a firewall." That works for a server you control end-to-end. It doesn't work when you want to give different agents different levels of access to the same server, or when you want to know after the fact what each agent actually called.

There's also a subtler problem: AI agents are prompt-injectable. A malicious tool response can instruct an agent to exfiltrate data or call a tool it shouldn't. A proxy that sits in the path of every response can catch this before it reaches the agent — but only if response filtering is built in from the start.

---

## What I built

[mcp-shield](https://github.com/nfvelten/mcp-shield) is a reverse proxy that sits between agents and MCP servers. It enforces per-agent policies before any tool call reaches the upstream.

```
Agent (Cursor, Claude, etc.)
        │  JSON-RPC
        ▼
  mcp-shield     ← auth, rate limit, payload filter, audit
        │
        ▼
  MCP Server (filesystem, database, APIs...)
```

A policy looks like this:

```yaml
agents:
  cursor:
    allowed_tools: [read_*]   # glob wildcards supported
    rate_limit: 30
    timeout_secs: 10
  claude-code:
    denied_tools: [write_file, delete_file]
    rate_limit: 60

default_policy:               # fallback for unlisted agents
  denied_tools: [delete_*]
  rate_limit: 10
```

Each agent gets an allowlist or denylist (with glob wildcards — `read_*` matches `read_file`, `read_dir`, etc.). The `tools/list` response is filtered before it reaches the agent — it only sees tools it's allowed to call. Agents not in the config fall back to `default_policy`, or are blocked entirely if none is set.

The pipeline applies in order: rate limit → auth → payload filter → upstream.

---

## Why Rust

The proxy sits in the hot path of every tool call. It needs to be fast and correct.

Rust's type system made the architecture natural. Each layer of the pipeline is a trait object. Transport, upstream, and audit backend are all traits — you can swap SQLite for a webhook, or HTTP transport for stdio, without touching the core logic. The policy map is an `Arc<HashMap>` shared across all middleware without copying.

The other reason was cross-compilation. MCP servers run everywhere — Linux, macOS, Windows, ARM boards. Rust compiles to all of them cleanly, especially once you drop OpenSSL for `rustls` (pure Rust TLS, no system dependency).

---

## The tricky parts

**stdio mode.** MCP has two transports: HTTP+SSE and stdio. In stdio mode, the agent and server communicate via stdin/stdout — there's no HTTP request to intercept. The gateway spawns the upstream server as a child process, reads from its stdout, writes to its stdin, and applies policies on each message in both directions.

**Redact vs. block.** The first version blocked any request containing a sensitive pattern. That's too coarse — sometimes you want to scrub the value and forward the sanitized request. Adding a `filter_mode: redact` option required threading `FilterMode` through the entire pipeline and writing a recursive JSON value walker (`redact_value`) that replaces matching string leaves with `"[REDACTED]"` while preserving the surrounding structure. Responses are always scrubbed regardless of mode.

**Prompt injection detection.** A `block_prompt_injection: true` flag enables seven built-in regex patterns covering instruction-override attacks, role reassignment, DAN-style jailbreaks, and prompt exfiltration attempts. The tricky part was deciding where these fit in the pipeline: they're checked *after* the `filter_mode` decision, always block, and their patterns don't get redacted — you want a hard rejection, not a scrub-and-forward.

**OpenTelemetry subscriber initialization.** Adding OTel tracing meant calling `.with(tracing_opentelemetry::layer().with_tracer(t))` conditionally on the `tracing_subscriber` registry. The problem is that each `.with()` changes the concrete type of the registry, making it impossible to branch without boxing or code duplication. The solution was a 4-branch match on `(json_logging, otel_enabled)`, each branch fully written out with concrete types. Ugly, but the compiler is happy.

**Multi-provider JWT.** The `auth:` config needed to accept either a single provider or a list — `#[serde(untagged)]` on an enum handles this transparently. Each provider in the list is tried in order; the first that successfully validates the token wins. OIDC discovery (`{issuer}/.well-known/openid-configuration`) is fetched once and cached for the process lifetime.

**Audit log.** `record()` is called in the request path and must be non-blocking. An unbounded channel separates the write from the disk. On graceful shutdown, `flush()` drops the sender (signals EOF) and awaits the background worker. Every write lands before the process exits.

---

## What it does now

- Per-agent allowlist / denylist with glob wildcards and `tools/list` filtering
- Sliding-window rate limiting: per-agent, per-tool, per-IP
- JWT / OIDC authentication — single provider or a list; Google, GitHub Actions, Auth0, Okta presets; JWKS caching
- Payload filtering with user-defined regexes; `block` or `redact` mode
- Response filtering — sensitive patterns scrubbed from upstream responses before reaching the agent
- Built-in prompt injection detection
- SQLite audit log with CLI; webhook backend; fan-out to multiple backends simultaneously
- Circuit breaker on each upstream — automatic half-open probe after recovery timeout
- `/health` endpoint reporting per-upstream status
- Config hot-reload via `SIGUSR1` or automatically every 30 seconds
- `X-Request-Id` on every response, recorded in audit and OTel spans
- Prometheus-compatible `/metrics`
- OpenTelemetry tracing via OTLP
- HTTP and stdio transports; TLS support

## The landscape

There are now several projects solving adjacent problems. [agentgateway](https://github.com/agentgateway/agentgateway) (Linux Foundation, 2,200+ stars) is the most mature — Rust core, WASM plugin system, multi-protocol. It's the right choice if you're building platform-level infrastructure.

mcp-shield is a different bet: a focused security proxy you can install with `cargo install mcp-shield` and configure with a single YAML file. No container runtime, no Kubernetes, no commercial tier. The tradeoff is that it won't grow into a service mesh — that's by design.

Um proxy no caminho de cada resposta pode interceptar isso antes de chegar ao agente — mas só se o response filtering for parte do design desde o início.

## O que construí

```
Agente (Cursor, Claude, etc.)
        │  JSON-RPC
        ▼
  mcp-shield     ← auth, rate limit, payload filter, audit
        │
        ▼

Uma política fica assim:

```yaml
agents:
  cursor:

A resposta do `tools/list` é filtrada antes de chegar ao agente — ele só vê as tools que pode chamar. Agentes fora da config herdam `default_policy`, ou são bloqueados completamente se não houver.

O pipeline se aplica em ordem: rate limit → auth → payload filter → upstream.

## Por que Rust

O proxy fica no caminho crítico de cada tool call. Precisa ser rápido e correto.

O sistema de tipos do Rust tornou a arquitetura natural. Cada camada do pipeline é um trait object. Transport, upstream e audit são todos traits — você pode trocar SQLite por webhook, ou HTTP por stdio, sem tocar na lógica central. O mapa de políticas é um `Arc<HashMap>` compartilhado entre todos os middleware sem copiar.

O outro motivo foi cross-compilation. Servidores MCP rodam em todo lugar — Linux, macOS, Windows, boards ARM. Rust compila para todos de forma limpa, especialmente depois de trocar OpenSSL por `rustls` (TLS puro em Rust, sem dependência de sistema).

## As partes difíceis

**Modo stdio.** O MCP tem dois transports: HTTP+SSE e stdio. No modo stdio, agente e servidor se comunicam via stdin/stdout — não há requisição HTTP para interceptar. O gateway spawna o servidor upstream como processo filho, lê do stdout dele, escreve no stdin, e aplica políticas em cada mensagem nos dois sentidos.

**Redact vs. block.** A primeira versão bloqueava qualquer requisição com padrão sensível. Isso é grosseiro demais — às vezes você quer remover o valor e encaminhar a requisição sanitizada. Adicionar `filter_mode: redact` exigiu passar `FilterMode` por todo o pipeline e escrever um walker recursivo de JSON (`redact_value`) que substitui folhas de string que fazem match por `"[REDACTED]"` preservando a estrutura. Respostas são sempre sanitizadas independente do modo.

**Detecção de prompt injection.** A flag `block_prompt_injection: true` habilita sete padrões regex cobrindo ataques de override de instrução, reassignment de papel, jailbreaks estilo DAN, e exfiltração de prompt. A parte difícil foi decidir onde isso se encaixa no pipeline: são checados *depois* da decisão de `filter_mode`, sempre bloqueiam, e seus padrões não são redactados — você quer rejeição hard, não scrub-and-forward.

**Inicialização do subscriber OpenTelemetry.** Adicionar tracing OTel significava chamar `.with(tracing_opentelemetry::layer().with_tracer(t))` condicionalmente no registry do `tracing_subscriber`. O problema é que cada `.with()` muda o tipo concreto do registry, tornando impossível branchar sem boxing ou duplicação de código. A solução foi um match de 4 branches em `(json_logging, otel_enabled)`, cada branch escrito completamente com tipos concretos. Feio, mas o compilador fica feliz.

**JWT multi-provider.** A config `auth:` precisava aceitar tanto um provider único quanto uma lista — `#[serde(untagged)]` num enum cuida disso de forma transparente. Cada provider na lista é tentado em ordem; o primeiro que valida o token com sucesso vence. A descoberta OIDC (`{issuer}/.well-known/openid-configuration`) é buscada uma vez e cacheada pelo tempo de vida do processo.

**Audit log.** `record()` é chamado no caminho da requisição e precisa ser não-bloqueante. Um channel separa a escrita do disco. No shutdown gracioso, `flush()` dropa o sender (sinaliza EOF) e aguarda o worker em background. Cada write aterra antes do processo encerrar.

## O que tem agora

- Allowlist / denylist por agente com wildcards glob e filtragem do `tools/list`
- Rate limiting por janela deslizante: por agente, por tool, por IP

- Tracing OpenTelemetry via OTLP
